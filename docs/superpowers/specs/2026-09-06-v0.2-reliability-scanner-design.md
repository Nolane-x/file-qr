# File QR v0.2 Reliability + Scanner Design

## Status

Approved product direction from the v0.1 follow-up discussion. This document defines only the first milestone in the staged roadmap. Later milestones for native OS integration, LAN discovery, optical FEC, signing, and auto-update remain out of scope here.

## Goal

Make the existing `drop → QR/code → receive` path substantially easier to use and more robust without adding a dashboard, accounts, history, cloud file storage, or a transport-selection UI.

The user-visible principle remains:

> **Drop. Scan. Receive.**

The v0.2 milestone adds browser camera scanning on Android and Windows, clipboard convenience, wake-lock protection, better transfer feedback, more resilient ICE setup, and a shorter production web hostname.

## Product invariants

1. File bytes do not enter the signaling service.
2. The rendezvous lifetime remains exactly 600,000 ms / 10 minutes.
3. A data channel already open at rendezvous expiry may finish.
4. The receiver capability remains the existing 50-bit Crockford receive code.
5. Network mode continues to use WebRTC RTCDataChannel.
6. Optical multi-frame `FQR1` remains native-only in v0.2.
7. No account, dashboard, history, cloud drive, chat, or manual transport selector is added.
8. Platform scope remains Windows + Android for the supported preview.
9. TURN is not claimed as enabled until a server-side TURN key is configured and production relay behavior is verified.

## Scope

### Included

- Rename the production static Worker from `file-qr-web` to `fileqr`, producing `https://fileqr.nolane-file.workers.dev` while leaving the old Worker deployment untouched as a temporary compatibility endpoint.
- Add `Scan QR` to the web receive flow on Android and Windows when camera APIs are available.
- Reuse the existing `qr@0.7.0` dependency and `qr/dom.js` camera decoder rather than introducing a second QR stack.
- Accept only File QR receive payloads from scanned QR data: either a valid receive code or a URL whose `receive` query parameter contains a valid receive code.
- Never navigate to an arbitrary URL obtained from a QR code.
- Add a `Paste` action for clipboard receive codes / File QR receive URLs.
- Add screen Wake Lock during active connection or transfer when supported.
- Add transfer ETA alongside existing throughput and byte progress.
- Add a bounded connection-establishment timeout and clearer connection failure states.
- Add Cloudflare STUN as a second public STUN endpoint while retaining Google STUN.
- Refactor WebRTC ICE configuration behind a function boundary so a future backend-provided TURN credential response can be inserted without changing call sites.
- Add tests for scanner payload parsing, camera lifecycle integration structure, wake-lock lifecycle, ETA formatting, ICE configuration, worker name, and deployment smoke-test target.
- Keep Windows and Android native packaging green because native network mode imports the shared web client.

### Explicitly deferred

- TURN relay activation and paid Cloudflare Realtime usage.
- Chunk resume across a newly-created peer connection.
- Android Share Sheet integration.
- Windows Explorer context-menu integration.
- LAN/mDNS discovery.
- Optical fountain/FEC or higher optical size caps.
- Windows code signing.
- Android production release signing.
- Native auto-update.

These become later staged milestones, not hidden scope in v0.2.

## UX design

### Idle receive row

The current receive code input remains primary fallback. Two small secondary actions are added beside it:

- **Paste** — reads clipboard text only after a user gesture, parses it as a File QR code/URL, and joins on success.
- **Scan QR** — opens an inline camera scanner only after a user gesture.

The layout must remain compact on desktop and stack cleanly on Android. No modal framework is introduced.

### Scanner state

Scanner UI is an inline panel inside the existing transfer stage with:

- live `<video>` preview;
- QR finder overlay canvas;
- short instruction text;
- `Cancel` action;
- permission/error status through the existing `aria-live` status line.

On Android the scanner requests the environment-facing camera. On Windows it requests the user-facing/default webcam, which is the common case when a phone displays the sender QR in front of a laptop camera.

The camera is opened only after `Scan QR` is clicked. The media stream is stopped immediately when:

- a valid File QR payload is decoded;
- the user cancels;
- receive begins;
- another transfer starts;
- the page unloads or resets.

A decoded arbitrary QR URL must not be opened. Instead, the scanner displays `Not a File QR receive code.` and keeps scanning.

### Payload parsing

Create one pure helper with this behavior:

```text
parseReceivePayload(input) -> normalized receive code | null
```

Accepted forms:

```text
ABCDE-FGHJK
ABCDEFGHJK
https://fileqr.nolane-file.workers.dev/?receive=ABCDEFGHJK
https://file-qr-web.nolane-file.workers.dev/?receive=ABCDEFGHJK
https://any-host.example/path?receive=ABCDEFGHJK
```

The host is deliberately not security-authoritative because the receive code itself is the capability and shared links may be hosted under a future custom domain. The parser extracts only `receive`; it never follows or navigates the URL. A URL without a valid `receive` value returns `null`.

### Paste behavior

Clipboard access occurs only on button click. The same `parseReceivePayload` helper is used. Failure is non-destructive and keeps the input focused.

### Wake Lock

If `navigator.wakeLock` exists, request a screen lock while state is one of:

```text
connecting, sending, receiving, verifying
```

Release it on:

```text
done, expired, cancelled, failed, idle, unsupported
```

When the document becomes visible again during an active state, reacquire the lock because browsers may release it while hidden. Wake-lock errors never fail a transfer.

### Progress + ETA

Keep the existing bytes, percentage, and throughput display. Add ETA only after enough progress exists to avoid nonsense estimates.

ETA is derived from average throughput since the current send/receive start:

```text
remainingMs = (totalBytes - transferredBytes) / bytesPerMs
```

Formatting:

- `< 60 s` → `~42s left`
- `< 60 min` → `~8m 12s left`
- otherwise → `~1h 04m left`

Before a stable estimate exists, show the current transport label instead.

## WebRTC reliability design

### ICE configuration boundary

Replace the hard-coded peer constructor configuration with:

```js
export function defaultIceServers() {
  return [
    { urls: ['stun:stun.cloudflare.com:3478'] },
    { urls: ['stun:stun.l.google.com:19302'] },
  ];
}

export function createPeerConnection({ iceServers = defaultIceServers() } = {}) {
  return new RTCPeerConnection({ iceServers });
}
```

This adds STUN provider redundancy without changing the direct-P2P privacy model.

### TURN-ready boundary

Do not put a long-lived TURN secret in `VITE_*` variables or browser JavaScript.

Future TURN activation will use a signaling endpoint that returns short-lived `iceServers` generated server-side from a Cloudflare TURN key. v0.2 only creates the call-site boundary required to pass such ICE servers into `createPeerConnection` later.

Production copy must continue to say direct P2P / no cloud storage and must not claim universal NAT connectivity or TURN fallback.

### Connection setup timeout

A receiver/sender that remains in `connecting` without an open data channel for 30 seconds transitions to `failed` with guidance to retry or use the native optical path.

The timer is cancelled when:

- the data channel opens;
- cleanup/reset occurs;
- the rendezvous expires;
- the user cancels.

This avoids indefinite connecting states while preserving the existing 10-minute rendezvous semantics.

### Connection-state diagnostics

Observe `RTCPeerConnection.connectionState` and surface concise failures for `failed` / terminal `closed` states. `disconnected` alone is not immediately fatal because browsers can transiently report it during network changes.

No auto-reconnect/resume is implemented in this milestone.

## Code boundaries

### New files

`apps/web/src/receive-payload.js`
- pure parsing of receive codes and URLs;
- no DOM dependency.

`apps/web/src/scanner.js`
- owns camera open/stop and QR frame loop;
- returns decoded strings through callbacks;
- does not know signaling or WebRTC.

`apps/web/src/wake-lock.js`
- owns acquire/release/reacquire behavior;
- failures are swallowed and observable only through return state.

### Modified files

`apps/web/index.html`
- receive convenience buttons;
- scanner inline panel/video/overlay.

`apps/web/src/main.js`
- orchestrates scanner, paste, receive flow, wake lock, ETA, and connection timeout;
- does not contain QR decoder internals.

`apps/web/src/webrtc.js`
- exports ICE configuration boundary and connection helper.

`apps/web/style.css`
- responsive scanner and receive action styles;
- reduced-motion behavior preserved.

`apps/web/wrangler.jsonc`
- Worker name `fileqr`.

`.github/workflows/pages.yml`
- smoke tests the new production hostname.

`README.md`
- documents v0.2 scanner and new URL;
- keeps TURN/non-claim boundaries explicit.

`tests/structure/web-ui.test.mjs`
- release-critical UI integration contracts.

New focused unit tests should be used for parser/formatting/ICE logic rather than relying only on source-string structural checks.

## Security and privacy

- Camera permission is user-initiated only.
- Media streams are local and immediately stopped after scanner completion/cancel.
- Scanned QR content is never navigated automatically.
- Clipboard reads are user-initiated only.
- No TURN long-term secret enters the client bundle.
- STUN additions reveal the normal WebRTC network metadata required for ICE but do not relay or store file payloads.
- Existing WebRTC encryption and signaling capability boundaries remain unchanged.

## Accessibility

- `Scan QR`, `Paste`, and `Cancel scan` are keyboard-focusable buttons.
- Scanner instructions and errors use the existing `aria-live` status region.
- Video is not relied on as the only status indicator.
- Reduced-motion settings continue to suppress non-essential animation.

## Success criteria

v0.2 is complete only when all of the following are true on one exact commit / merge lineage:

1. Android Chromium web can scan a sender File QR session QR and join automatically.
2. Windows Chromium web with a webcam can scan the same QR and join automatically.
3. Plain code entry remains functional.
4. Paste accepts both codes and File QR receive URLs.
5. Arbitrary QR URLs are never opened.
6. Camera resources are released on success, cancel, reset, failure, and page exit.
7. Active transfers request wake lock where supported without making it a hard dependency.
8. Transfer progress includes a bounded ETA estimate.
9. A stalled connection no longer remains indefinitely in `connecting`.
10. Cloudflare + Google STUN are configured through a testable ICE boundary.
11. No TURN availability claim is made.
12. Web deploys and smoke-tests successfully at `https://fileqr.nolane-file.workers.dev/`.
13. Windows and Android native builds remain green.
14. No unrelated v0.3+ features are smuggled into the milestone.
