# File QR v0.4 — Session Reliability Design

## Goal
Make a File QR receive code a real 10-minute lease rather than a one-shot ticket, allow sequential receivers during that full lease, and make interrupted network transfers retry/resume safely without changing the product promise that file bytes are not stored by the signaling service.

## Product contract
- A newly created receive code is valid for exactly 600,000 ms from `createdAt`.
- The code remains discoverable for the full lease even after one or more completed transfers.
- At most one receiver transfer attempt is active at a time.
- A receiver that disconnects releases the active slot; another receiver may join while the lease remains open.
- A transfer attempt admitted before `expiresAt` may finish after `expiresAt`.
- No new receiver may be admitted at or after `expiresAt`.
- Sender signaling stays attached until lease expiry or explicit sender cancellation.
- Signaling never stores file bytes.
- Sender file bytes remain local until a data channel opens.

## Root-cause corrections
The v0.3 flow marks the room `consumed` as soon as the sender data channel opens, stops the countdown, and closes the sender signaling socket after one transfer. Those behaviors contradict a reusable ten-minute lease and must be removed rather than patched around.

## Session model
Persist a lease record:

```js
{
  code,
  senderToken,
  createdAt,
  expiresAt,
  attemptCounter
}
```

`consumed` is removed. Durable Object websocket tags remain `sender` and `receiver`; only one live receiver socket is accepted at a time. A disconnect immediately makes the receiver slot available again.

The room alarm still fires at `expiresAt`, but expiry semantics change:
- sender/receiver signaling sockets that are only waiting/negotiating are closed with the expiry code;
- an already-open data channel is not owned by the Worker and may continue independently;
- room storage is deleted at expiry after closing signaling sockets;
- no later join is possible because room state is gone/expired.

## Transfer attempts
Every receiver admission receives an incrementing `attemptId`. `peer-ready` includes that ID. The sender creates a fresh `RTCPeerConnection` and data channel per attempt. Attempt teardown must not destroy the lease object, sender file, QR, countdown, or sender signaling connection.

A sender can therefore serve:

```text
attempt 1 -> failed -> slot released
attempt 2 -> receiver A resumes -> complete
attempt 3 -> receiver B starts from zero -> complete
```

## Resume protocol v2
Upgrade the control protocol while preserving v1 decode rejection instead of ambiguous compatibility.

Control messages:

```text
file-offer { fileId, name, size, type, chunkSize }
resume-request { fileId, offset }
transfer-complete { fileId, size }
complete-ack { fileId, size }
```

`fileId` is a sender-local random identifier stable for the ten-minute lease. Receiver resume is allowed only when `fileId`, `name`, `size`, and `type` match the partial sink metadata.

The receiver persists a partial file in OPFS with lease/file identity metadata. On reconnect in the same browser profile it reopens the partial, reports its current byte offset, and appends from there. Memory fallback may resume only while the current page/runtime remains alive; a reload is allowed to restart from zero.

The sender streams `file.slice(offset)` using the existing bounded-buffer flow. Receiver rejects offsets outside `[0, size]` and rejects a `transfer-complete` whose written byte count is not exactly `size`.

## WebRTC recovery
Keep direct WebRTC as the preferred transport.

- ICE servers continue to include Cloudflare STUN and Google STUN.
- Add an explicit ICE state machine around each attempt.
- On `disconnected`, wait a short grace period before declaring failure.
- On `failed`, perform one `restartIce()` renegotiation for that attempt before surfacing failure.
- A new receiver reconnect creates a fresh attempt even when the previous peer object is irrecoverable.
- Transport diagnostics expose `Direct`, `Relay`, or `Unknown` only as informational UI; users never select transports manually.

## TURN boundary
TURN is optional infrastructure, not a browser secret.

The signaling service may expose `POST /v1/turn-credentials` only when server-side TURN configuration exists. The endpoint returns short-lived ICE credentials and never returns the long-lived TURN key. Clients merge returned TURN servers into `iceServers`; when the endpoint is unavailable they continue direct/STUN behavior without failing session creation.

TURN activation is a deployment/configuration gate. Tests and code must support the boundary before any claim that relay is live.

## Sender lifecycle
The sender state separates lease state from attempt state.

Lease states:
`preparing -> available -> expired|cancelled`

Attempt states:
`idle -> connecting -> sending -> completed|failed -> idle`

A completed attempt returns the sender to `available` with the same QR/code and remaining countdown. The sender may show cumulative transfer count but must not create history/dashboard UI.

## Receiver lifecycle
Receiver failure copy must distinguish:
- code expired;
- receiver slot busy;
- direct path failed after ICE restart;
- partial file saved and retryable;
- relay unavailable/not configured.

Retry uses the same code and, when a compatible OPFS partial exists, requests its offset automatically.

## Security and privacy
- Sender token remains required for the sender socket.
- Receiver capability remains the 50-bit receive code.
- One receiver at a time limits accidental fan-out and simplifies sender consent semantics.
- Partial files are local browser storage only and are cleaned after successful save or when the user explicitly discards/restarts.
- No file bytes enter the Worker.

## Verification
Required automated evidence:
- exact 600,000 ms expiry tests;
- completed transfer does not consume the lease;
- sequential receiver admissions before expiry;
- receiver admission denied at/after expiry;
- attempt started before expiry may continue at application layer;
- resume offset validation and chunk streaming from offset;
- OPFS partial metadata compatibility and append behavior;
- one ICE restart maximum per attempt;
- optional TURN credential fetch does not block direct mode;
- structural tests proving sender countdown/signaling are not stopped after a single completed transfer.

Required runtime evidence before release claim:
- full CI;
- Cloudflare signaling deploy health/session smoke test;
- web production deploy smoke test;
- Windows and Android native builds;
- at least one browser-level interrupted-transfer simulation. Physical cross-network/NAT verification remains `UNKNOWN` until run on real networks.

## Non-goals
- No cloud file storage.
- No concurrent multi-receiver broadcasting.
- No LAN discovery in v0.4.
- No optical protocol changes in v0.4.
- No UI visual reconstruction beyond reliability states needed by this protocol.
