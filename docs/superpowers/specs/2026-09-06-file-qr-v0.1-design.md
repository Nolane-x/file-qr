# File QR v0.1 Design

## Product truth
File QR is a deliberately small transfer product for Windows and Android. The web surface is the zero-install path: drop a file, show a QR code and short receive code, then transfer directly over WebRTC. The installed Windows/Android app keeps the same interaction model and adds an offline optical transport that repeatedly streams QR frames between a screen and a camera.

## Supported surfaces
- Web sender/receiver: Chrome and Edge on Windows, Chrome on Android.
- Native app: Windows and Android only.
- Unsupported in v0.1: iOS, macOS, Linux, accounts, history, cloud storage, chat, multi-recipient broadcast.

## Ten-minute rule
A rendezvous session is joinable for exactly 600 seconds from creation. At expiry, QR/code lookup and signaling are invalidated and ephemeral signaling state is destroyed. A WebRTC transfer that has already opened its data channel may finish after rendezvous expiry because the signaling service is no longer on the file path.

## Privacy and security
- File bytes never pass through the signaling service.
- Signaling stores only ephemeral rendezvous state.
- Receive codes use cryptographically random Crockford Base32 characters and are grouped for readability.
- WebRTC provides encrypted DTLS/SCTP transport.
- A session accepts one sender and one receiver in v0.1.
- Session expiration is enforced server-side with a Durable Object alarm, not just a client timer.

## Web architecture
- Vite static frontend deployed with GitHub Pages.
- A Cloudflare Worker + Durable Object provides session creation and WebSocket signaling.
- Sender creates the session, publishes an SDP offer and ICE candidates through signaling, renders the receive URL as QR, and streams the selected file in ordered 64 KiB chunks over RTCDataChannel.
- Receiver can arrive from QR URL or by entering the short code on the homepage.
- Receiver writes into OPFS when available and otherwise falls back to an in-memory Blob path with an explicit size warning.

## Native architecture
- Tauri 2 provides a single native shell for Windows and Android.
- The native UI reuses the same visual language and shared transfer/optical protocol modules.
- Network mode can use the same WebRTC path.
- Offline optical mode encodes a file into repeated QR frames. Each frame carries protocol version, stream id, sequence number, total frame count, CRC32, and base64url payload.
- Receiver deduplicates frames, validates CRC32, reports missing progress, and reconstructs the original file once all frames arrive.
- Optical v0.1 intentionally uses repeated frames rather than pretending to be a fountain-code implementation. The protocol is versioned so a future FEC/fountain transport can replace the frame scheduler without changing UI/session semantics.

## Interaction model
Primary homepage state has one dominant send affordance and one compact receive-code affordance. Windows/Android download buttons are visible but visually secondary. UI states are explicit: idle, drag-over, preparing, ready, connecting, sending, receiving, verifying, done, expired, cancelled, failed, unsupported.

## Visual direction
Dark graphite canvas, warm near-white typography, one electric accent, large typographic hierarchy, restrained glass/blur only where it conveys layering, no dashboard chrome, no decorative card grid. QR is rendered high-contrast with a full quiet zone and no logo overlay. Motion communicates transfer state and respects reduced-motion preferences.

## Repository layout
- `apps/web`: web sender/receiver.
- `apps/native`: Tauri Windows/Android shell with optical mode.
- `packages/core`: shared session, transfer and optical framing logic.
- `services/signaling`: Cloudflare Worker + Durable Object.
- `tests`: dependency-light protocol, signaling and structural tests.
- `.github/workflows`: tests, Pages deployment, native build/release.

## Release boundary
v0.1 is considered verified only when Node protocol tests pass, web builds, signaling type/build checks pass in CI, Windows Tauri build passes on `windows-latest`, and Android APK build passes on an Android-capable GitHub runner. Runtime camera/optical quality remains an empirical device-matrix claim and must not be described as universally verified solely from CI.
